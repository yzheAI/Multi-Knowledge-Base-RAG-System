# BM25

## 1. 模块概述
BM25是Retrieval Pipeline中的关键词检索模块，
主要用于根据Query与Chunk之间的关键词匹配程度进行检索。
本项目使用BM25Okapi实现，使用jieba对中文Query和Chunk进行分词。

BM25 与 FAISS的关系：
- FAISS：基于Embedding语义检索
- BM25：基于关键词匹配的稀疏检索
- Hybrid Retrieval：融合FAISS与BM25的检索结果

## 2. 为什么需要BM25
单独使用FAISS语义相似度检索存在着一定局限：
当Query中含有：
- 专业术语
- 特定名称
- 精确关键词
- 数字或特殊表达

仅依靠语义相似度检索召回目标Chunk的效果将会下降。

BM25通过关键词匹配计算Query和Chunk的相关性，
因此可弥补FAISS语义检索在精确关键词匹配方面的不足。

本项目最终使用：FAISS+BM25进行混合检索

## 3. BM25基本原理
BM25是一种基于词频统计的相关性排序算法。
它主要使用以下指标：
- Query中的关键词是否出现在文档中
- 关键词在当前文档中出现频率
- 关键词在整个语料中的稀有程度
- 文档长度

### 3.1 TF
Term Frequency，词频。
表示某个词在当前文档中出现的频率。

### 3.2 IDF
Inverse Document Frequency，逆文档频率。
一个词出现在越多的文档中，区分能力也就通常越弱，越少见的词区分能力通常越强。

### 3.3 文档长度
BM25会考虑文档长度，避免长文档仅仅因为包含更多的词而获得高分。

## 4. 中文分词
BM25需要接收Token序列，而中文文本没有天然的空格分隔，同时也会出现短语、成语等现象，
因此本项目使用
```text
jieba.cut()
```
对Chunk和Query进行分词。
例如：
```text
人工智能在工业互联网中的应用
```
经过分词后可以得到：
```text
人工智能 / 在 / 工业互联网 / 中 / 的 / 应用
```
最终转换为列表形式：
```text
[
    "人工智能",
    "在",
    "工业互联网",
    "中",
    "的",
    "应用"
]
```
需要保证Query和Chunk的分词方式一致。

## 5. BM25Store数据结构
本项目没有在业务代码中直接使用BM25Okapi，而是封装BM25Store类，
主要维护三个状态：
```text
self.tokenizer
self.ids
self.bm25
```

### 5.1 tokenizer
保存所有Chunk分词后的结果，使用list[list[str]]表示
```text
[
    ["人工智能", "应用", "工业互联网"],
    ["机器学习", "人工智能"],
    ["数据库", "数据", "存储"]
]
```
以上tokenizer并不是指tokenizer对象，而是：
所有Chunk的Token序列组成的语料库。

### 5.2 ids
用于保存Chunk ID
```text
[101, 102, 103]
```
ids与tokenizer中的语料位置一一对应，用于将BM25返回的语料库index映射为业务层的chunk_id。
即通过ids完成映射。
### 5.3 bm25
bm25在系统中作为BM25Okapi对象。
它根据完整的Token语料库建立BM25索引结构。

## 6. 添加文档
核心方法：
```text
add_documents()
```
处理流程：
```text
documents
    ↓
提取 chunk_id
    ↓
 提取 text
    ↓
 jieba分词
    ↓
加入tokenizer
    ↓
  加入ids
    ↓
重新构建BM25Okapi
```

### 6.1 提取Chunk ID
```text
new_ids = [
    doc["chunk_id"]
    for doc in documents
]
```

### 6.2 提取文本
```text
new_texts = [
    doc["text"]
    for doc in documents
]
```

### 6.3 分词
```text
[
    list(jieba.cut(text))
    for text in new_texts
]
```

### 6.4 增量添加
```text
self.ids.extend(new_ids)
```

### 6.5 重新构建BM25
```text
self.bm25 = BM25Okapi(
    self.tokenizer
)
```
由于语料库发生变化，因此根据完整语料重新构建 BM25。

## 7. BM25 检索流程
核心方法：
```text
search()
```

完整流程：
```text
User Query
    ↓
 jieba 分词
    ↓
query_tokens
    ↓
 get_scores
    ↓
enumerate排序
    ↓
index->chunk_id
    ↓
  Top-K
    ↓
返回检索结果
```

### 7.1 Query分词
```text
query_tokens = list(
    jieba.cut(query)
)
```
将用户问题以与Chunk相同的处理方法进行分词处理。
例：
```text
query: 人工智能在工业互联网中的应用
query_tokens:
[
    "人工智能",
    "在",
    "工业互联网",
    "中",
    "的",
    "应用"
]
```

### 7.2 BM25计算分数
```text
scores = self.bm25.get_scores(
    query_tokens
)
```
进行bm25关键词匹配，返回一个分数数组。
分数在数组中的位置与ids的位置下标一一对应，
因此 scores 的下标是语料库位置，而不是 chunk_id。

### 7.3 排序
使用
```
enumerate(scores)
```
将index+score绑定起来，然后进行排序：
```text
sorted(
    ...,
    key=lambda x: x[1],
    reverse=True
)
```
按照BM25分数从高到低排序，例如：
```text
排序前：
[
    (0, 3),
    (1, 5),
    (2, 4)
]

[
    (1, 5),
    (2, 4),
    (0, 3)
]
```

### 7.4 Index到Chunk ID的映射
BM25返回的是index而不是chunk_id，因此需要通过self.ids[idx]完成映射。
例如：
```text
self.ids = [101, 102, 103]
```
使用 BM25 返回的语料库 index 作为下标访问 self.ids，从而获得对应的 chunk_id。
```text
BM25 index
    ↓
self.ids[index]
    ↓
chunk_id
```

### 7.5 检索结果格式
BM25最终返回：
```text
{
    "chunk_id": ...,
    "score": ...,
    "source": "bm25"
}
```
其中：
- chunk_id：对应Chunk的数据库ID
- score：BM25相关性分数
- source：表示结果来自BM25
source 用于后续 Hybrid Retrieval 区分 FAISS 和 BM25 的结果来源。

## 8. 删除文档
核心方法：
```text
delete_documents()
```

处理流程：
```text
需要删除的 chunk_ids
        ↓
zip(ids, tokenizer)
        ↓
过滤被删除 Chunk
        ↓
重新生成 ids
        ↓
重新生成 tokenizer
        ↓
重新构建 BM25
```

### 8.1 为什么使用zip
self.ids与self.tokenizer需要保持一一对应，
通过：
```text
zip(
    self.ids,
    self.tokenizer
)
```
通过zip()可以同时获取chunk_id和对应的Token序列，从而在删除指定Chunk时保留两者之间的对应关系。

### 8.2 删除后重新构建BM25
删除Chunk后，语料库发生变化，因此重新：
```text
BM25Okapi(
    self.tokenizer
)
```

## 9. 持久化
为了避免每次启动程序都需要重建BM25，本项目使用pickle对BM25状态进行持久化。
保存：
```text
data = {
    "tokenizer": self.tokenizer,
    "ids": self.ids,
    "bm25": self.bm25
}
```
保存位置：
```text
<kb_path>/bm25.pkl
```

## 10. 加载
启动或加载知识库时，需要从bm25.pkl中获取数据：
```text
bm25.pkl
    ↓
pickle.load()
    ↓
恢复 tokenizer
恢复 ids
恢复 bm25
```
如果文件不存在，则初始化为空。

## 11. VectorStore 中的BM25
VectorStore负责统一管理知识库的FAISS索引和BM25索引。
在VectorStore初始化时创建BM25Store：
```text
self.bm25 = BM25Store()
```
之后由 VectorStore 统一管理 BM25 的创建、添加、删除、保存和加载，并保证 FAISS 与 BM25 中的 Chunk 数据保持同步。
例如添加Chunk时，VectorStore.add()在将Embedding和chunk_id添加到 FAISS后，
会同时将Chunk的文本和chunk_id交给BM25Store：
```text
VectorStore.add()
       │
       ├──→ FAISS：保存 Embedding + chunk_id
       │
       └──→ BM25Store：保存文本分词结果 + chunk_id
```
删除Chunk时同样由VectorStore.delete()同步处理两套索引：
```text
VectorStore.delete()
       │
       ├──→ FAISS：删除对应 chunk_id
       │
       └──→ BM25Store：删除对应 Chunk
```
持久化和加载时，VectorStore也统一管理两套索引：
```text
VectorStore
    │
    ├── FAISS
    │     └── faiss.index
    │
    └── BM25
          └── bm25.pkl
```
因此，VectorStore可以看作知识库检索索引的统一管理层，而BM25Store则负责具体的BM25数据结构和检索逻辑。

## 12. 当前实现的优点

- 基于关键词匹配，与FAISS形成互补
- 通过jieba支持中文文本检索
- 与Chunk ID建立映射
- 支持增删与持久化
- 按知识库独立管理

## 13. 当前不足与优化方向

### 13.1 中文分词问题

当前直接使用：
```text
jieba.cut()
```
进行分词，对于专业领域知识库，通用词典可能无法很好的识别专业术语。

后续可考虑：
- 添加领域专业词典
- 对专业术语进行词典维护
- 对数字、英文缩写进行针对性处理

### 13.2 优化BM25参数
当前使用BM25Okapi默认参数，
后续可以针对实际知识库数据调整BM25的参数，例如k1和b，
并通过Recall@K、MRR等指标进行实验，对比不同参数下的检索效果。


### 13.3 增加检索前处理
当前Query主要经过jieba分词后直接进入BM25，后续可增加：
```text
Query
 ↓
文本清洗
 ↓
停用词处理
 ↓
关键词规范化
 ↓
jieba 分词
 ↓
BM25
```
减少无意义词语对检索结果的影响。
